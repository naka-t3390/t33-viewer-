T33 Drive ビューア — 端末縦型画面の再現パネル

設計書 / 2026-11-28 / 対象リポジトリ t33-viewer(ブランチ feat/cockpit-panel)

1. 目的

ビューアで走行セッションを開いたとき、KYV46 端末の記録中(縦向き)画面と同じものを、 動画・地図と同期して見られるようにする。走行の映像と、そのときモーター・電池・ シフトがどうだったかを、端末の画面と同じ並びで突き合わせられるのが狙いである。

再現の元は端末アプリ T33Monitor の ui/dashboard/DashboardScreen.kt の RecordingDashboardPortrait(main にマージ済み)。信号の読み方の出どころは data/can/CanSignalSpec.kt ただ一つで、係数・符号・ビット幅はそれと 1 対 1 で移植する。 独自解釈は持ち込まない。

2. 時刻合わせ(ここを間違えると全部ずれる)

基準は _video.json の最初の segments[].start_ms。ビューアは既にこれを startMs として持っている(js/parse.js の buildViewModel)。 CAN ログの 1 行の時刻は 

t[秒] = (timestamp_ms - startMs) / 1000

再生位置は js/viewer.js の globalTime() = 現セグメントの baseOffsetSec + video.currentTime。地図のマーカーとグラフのカーソルがこれで動いているので、 パネルも同じ globalTime() を使う。GPS の時刻は端末の時計と約 5 秒ずれるので、 同期の基準には使わない。

検算(2026-11-28 セッション 102230、startMs=1795828951258)

検算項目区間
前モータ回転 1DA が −5 rpm 未満(後退)599.88 〜 617.00 s
シフトが R(1D4 b5 の bit1-2 == 1)600.21 〜 618.01 s(17.8 秒)

二つが 0.3〜1.0 秒以内で一致するので、この時刻基準は正しい。 この一致を回帰テストに固定する(合成フィクスチャで同じ形を作る)。

3. 性能の制約と間引きの方針

CAN ログは 1 セッションで 250〜360 万フレーム(平文 90〜134MB)。ブラウザで全部を オブジェクト配列に持つことはできない。

  • ダウンロードは増やさない。 既に軌跡補正(dead-reckoning.js)のために CAN ログを 1 回落としてストリーミング解析している(js/can-signals.js の parseCanSignalsFromBuffer)。その同じ 1 パスの中でパネル用の信号も拾う。
  • 20Hz のグリッドへ間引く。 端末は CAN スナップショットを 50ms ごとに公開しているので、 20Hz が端末と同じ刻みになる。各バケットは平均ではなく最終値を採る (平均するとトルクの山が鈍り、端末の表示と変わってしまう)。
  • 10Hz の信号は前値保持。 SOC・水温・油温・吸気温・エンジン負荷は 10Hz なので、 20Hz グリッドでは 1 つ飛びになる。端末も最後に来た CAN 値を保持して表示しているので、 同じく前値を保持する。値が一度も来ていない区間は NaN のままにして 「未取得」と区別する。
  • 列ごとの Float32Array で持つ。 630 秒 × 20Hz = 12,600 行 × 18 列 ≒ 0.9MB。オブジェクト配列(1 行 1 オブジェクト)にはしない。
  • ID の判定は整数キーの switch。 18 個の ID を startsWith の連鎖で判定すると 1 行ごとに最大 18 回の比較が走る。 3 文字を文字コードから整数キーにして 1 回の switch で分岐する。

派生値(端末と同じ式)

  • モーター出力 kW = トルク[Nm] × |回転[rpm]| ÷ 9549(cockpitModelOf)
  • 前後配分 = |前トルク| : |後トルク| の百分率。両方 0 のときは 0 : 0 (データが無いだけなのに「50:50 で配分されている」と見せないため)
  • 電池電力 kW = 電圧 × 電流 ÷ 1000。符号はそのまま(負が放電)

未解決: 12bit の上限がカタログ値に届かない。 12bit 符号付きの上限 ±2047 カウント = ±255.9 Nm が、公称のフロントモータートルク(330Nm 級)に 足りない。2026-11-28 の実測は前 +62.75 Nm までで、飽和まで大きな余裕があり、どちらが起きるかは まだ見えていない。係数には手を入れない。|トルク| が 250 Nm を超えたときだけ パネル側で飽和の疑いを示す印を出す。

5. 表示の約束(端末と同じ)

端末は「裏付けのない値を数字らしく見せない」約束を持っている(CockpitValue.verified、 色は T33Colors.Unverified)。パネルも同じにする。

  • CAN から取れていない値は 0 か --- をグレーで描く
  • 前後モーターは、トルクと回転がどちらも 0 の間は「取れていない」とみなしてグレー
  • シフトが未取得なら -、READY / e-Pedal は消灯
  • 再生位置が CAN ログの範囲外(記録開始前・CAN が落ちた後)なら、全体をグレーにして 「CAN なし」と出す。もっともらしい値を置かない

6. 画面の置き場所

.mid の右枠(いまグラフがある場所)をグラフと端末画面で切り替える (2026-11-28 の所有者指定)。ヘッダ横のボタンで切り替え、選択は localStorage に残す。 

.mid  [ 動画 16:9 / 42vh ][ グラフ ⇄ 端末画面(縦 9:19.5) ]
#map  [ 全幅。残りの縦を吸収 ]
  • 端末画面は 9 : 19.5(KYV46 の画面比)を保ち、枠の中で中央に置く。 高さは clamp(420px, 68vh, 760px)。.mid の行が伸びたぶんは #map(flex:1)が吸収する
  • 760px 以下(スマホ)では既存のとおり縦積みになり、動画の下に来る
  • 配色は端末と同じ暗色で固定し、ビューアのテーマには追従させない。 端末画面の再現なので、明るいテーマの中でも「端末の画面」として読めるほうがよい
  • グラフに戻せば、グラフのクリックによるシーク(既存機能)はそのまま使える

7. e-4ORCE 俯瞰図

端末の ui/e4orce/E4orceTopView.kt の drawTopView を Canvas 2D へ移植する。

  • リングと目盛り。四輪はリング上の 225/315/135/45 度に置く
  • 四輪の弧: 実測の車輪速から幾何で決まるぶん(ackermannFactors)を引いた残り (スリップ)を、その輪の位置から力の向きへ伸びる弧で描く。内輪がオレンジ、外輪が薄い青。 弧の長さと太さ、タイヤの大きさが力の強さを表す
  • 車体は真上から見た T33 のシルエット(輪郭の座標列をそのまま移植)
  • 重心ポイント(赤)と残像:
    • 横方向 = 旋回横G v² / (R · g)。R は舵角から WHEELBASE_M / tan(舵角 / 17.3)。0.35G で振り切れる。 左旋回(舵角が正)で右(+x)へ寄る
    • 前後方向 = (0B4 の生値 − 31959) / 3500。加速で後ろ(+y)、減速で前(−y)
    • 合成ベクトルの長さは 1.0 に収める。可動範囲はリング半径の 0.58 倍
    • 残像は 1,400ms 保持・33ms 間隔で記録し、残り寿命の 2 乗で薄く小さくなる

端末では残像は「実時間が進むたび」に記録される。ビューアは再生位置の時刻で 記録するので、早送り・巻き戻し・シークでも軌跡が正しく付いていく (時刻が巻き戻ったらバッファを捨てる。端末の CenterOfGravityTrail と同じ扱い)。

9. テスト戦略

ユニットテスト(node --test)

  • デコード(表駆動): 12bit 符号付きトルク、s16 回転の負値、上位 10bit 電圧、 上位 11bit 符号付き電流(負が放電)、SOC、発電回転 ÷5.1207、車速 ÷102.086、 水温 −40 / 油温 −30 / 吸気 −50、負荷のクランプ、シフトの 4 値、READY、e-Pedal、 舵角の左正・右負、四輪の割り当て
  • ストリーミングの境界: 行の途中・CRLF・壊れた 16 進・29bit 拡張 ID・ データ長不足で取りこぼさない / 取り違えない
  • グリッドとサンプラ: バケット最終値、前値保持、一度も来ていない区間は NaN、範囲外の t では「CAN なし」
  • 時刻合わせの回帰: 600 秒から R + 前回転が負のフィクスチャで、 cockpitAt(600.5) が R、cockpitAt(590) が D
  • 表示モデル: kW の式、前後配分が両方 0 で 0:0、未取得がグレー
  • 俯瞰図の幾何: 弧の長さ・太さ・タイヤ倍率・重心オフセット(左旋回で +x、 加速で +y)・残像の減衰。端末側の Kotlin テストと同じ期待値をミラーする

実データ照合(done の定義)

  1. _verify_cockpit.html で log/20261128/094619/ と log/20261128/102230/ を読み、JS モジュールの出す値を独立実装 (Python)の値と突き合わせる(全区間の min/max と代表時刻)
  2. 同じハーネスで t = 600s 付近を再生し、シフト R・前後回転が負が パネルに出ることを目視(スクリーンショット)で確認
  3. 動画を再生して、パネルの値・地図のマーカー・グラフのカーソルが同じ時刻で動くことを確認

10. やらないこと

  • 端末アプリ(Torque2)側のコードは変更しない
  • トルク係数 0.125 Nm/count には手を入れない(12bit 上限の矛盾は未解決のまま残す)
  • 094619 の CAN が gz 化されていない(平文 134MB)件は今回直さない。 既存の軌跡補正でも同じ量を落としているため、別の作業として分ける
  • OBD 由来の CSV(t33_<時刻>.csv)の表示は今のゲージ帯のまま変えない
